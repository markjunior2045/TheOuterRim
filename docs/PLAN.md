# PLAN.md — Outer Rim digital

Task plan, ordered by dependency. Each task is meant to fit one Claude Code session, with a **Done when** criterion and the tests that prove it.

**This plan is a guide, not a contract.** Tasks may be done out of order, split, merged or replaced, as long as that does not hurt the project. When the order changes for good, update this file. Dependencies are listed so that skipping ahead is a conscious choice, not an accident.

Rule IDs (`R-x.y`) refer to `RULES.md`. Decisions live in `DECISIONS.md`. No time estimates, by decision.

**Status legend:** `DONE` · `REVIEW` (done, awaiting human check) · `TODO` · `BLOCKED` (needs input) · `DEFERRED` (intentionally postponed)

---

## Conventions

- **Done means:** tests pass, new behaviour cites its rule IDs in code comments and test names, docs are updated if a decision was made, one branch and at least one commit per task.
- The rules core has no `UnityEngine` references (see `DECISIONS.md` §7). The Unity layer displays state and sends commands.
- Core behaviour is verified with `dotnet test`, not by playing in the editor.
- Anything ambiguous in the rules is marked `[?]` in `RULES.md` and asked about, not guessed.
- Plain Git, no LFS. Raw source images do not go in the repository.

---

## Roadmap (owner decision, 2026-11-04)

The phases below group tasks by subject; this is the order they are worked in:

1. **Patterns:** T2.1, the inventory of objects, effects, conditions, targets and timings, from the 242 base cards plus the `[UB]` extension points in `RULES.md`. The expansion cards are not transcribed for this.
2. **Data:** T2.2 (schema), T0.5 (map geometry), T2.4 (small data sets: patrols, player board, sheets).
3. **Core:** Phase 1, using real data wherever it already exists.
4. **V0:** T3.1, seeded automated games in a terminal.
5. **Prototype:** T0.4 (Unity), then T3.2 to T3.5, adding one feature at a time. The prototype shows the TTS scans as they are (`DECISIONS.md` §3, prototype exception).
6. **After V1:** see the last section. Templates, translation, animation and sound come only once the game works.

## Phase 2 — Content

### T2.1 — Effect inventory · `DONE` (`docs/EFFECTS.md`, approved 2026-11-05)
- Classify every card's effect, condition and target types, plus card and component types, into `docs/EFFECTS.md`.
- **Done when:** every base card maps to a known effect type or is listed as a custom exception, and every `[UB]` mechanic in `RULES.md` has a named extension point.
- Classification, not transcription: it sets the card data format. Works from the T2.8 transcriptions. Expansion cards are not transcribed first; their structural mechanics come from the `[UB]` rules, and card-specific effects are added when the expansion is transcribed.

### T2.2 — Data schema and validator · `REVIEW` (2026-11-05)
- JSON schema for cards, effects, characters, ships and **content packs** (id, version, dependencies); validator; stable IDs.
- **Done when:** the validator rejects malformed cards and unknown effect types.
- **Delivered:** `docs/DATA_FORMAT.md`; `data/schema/registry.json` (effects, conditions, timings, events, selectors, card kinds, from `EFFECTS.md`); base pack manifest `data/packs/base/pack.json`; English strings `data/packs/base/loc/en.json` generated by `tools/build_loc.py`; `tools/validate_data.py` with 19 tests in `tools/tests/` (unknown effect, condition, timing, handler, field, kind, space, missing parameter or text key, duplicate id, bad amount or enum, unknown dependency).
- **Sample:** market gear (15) and cargo (10) encoded and valid. The remaining kinds (job, bounty, ship, encounter, databank, character, ship sheet, contact, AI) are added to the registry and encoded deck by deck in T2.4 to T2.6.
- The C# loader reads the same registry when the effect engine is built (T2.3); the Python validator stays as the data-pipeline check.

### T2.8 — Card transcription in batches · base game `DONE` (2026-11-04), expansion `DEFERRED` (with the Unfinished Business pack, after V1; owner decision 2026-11-04)
- Transcription came first because the card patterns found here drive the core design (T2.1).
- Raw printed text into JSON, format `outer-rim-transcription/0.10` (`docs/TRANSCRIPTION_FORMAT.md`). Mapping text to effects happens later, in T2.1/T2.2.
- Each batch starts with an icon legend (market deck backs, reputation icons, die faces) and ends with the owner reviewing the cards listed under `verify`.
- English first; Portuguese through the localization files.
- **Pilot · `DONE` (2026-11-04):** 10 base cargo cards and 5 Lothal/Mon Calamari encounters; format validated; about 850 image tokens per market card and 1,700 per encounter.
- **Batches (base game) · `DONE`:** 242 of 242 cards, all `verify` items reviewed by the owner.
  - [x] Market: bounty, cargo, gear, job, luxury, ship (70)
  - [x] Databank (53)
  - [x] Encounters: all seven decks (70)
  - [x] Characters (8), ship sheets (9 unique), contacts (22), AI smuggler deck (10)
  - Patrol tokens and player boards are not cards and are not counted in `PROGRESS.md` (owner decision); their printed values are transcribed in `data/transcription/patrols/` and `data/transcription/player-boards/` (2026-11-05).
- Progress per pack: `data/transcription/PROGRESS.md` (regenerated after every batch).
- **Batches (Unfinished Business):** after the base game, same split; decide first which image version to read from (`DECISIONS.md` §9).
- **Done per batch when:** the JSON parses, every card in the deck is present, and the batch is reviewed. Validation against the data schema comes once T2.2 exists.
